# Definition of Done (DoD)

## 1. Умови, за яких історія вважається завершеною

Користувацька історія (User Story) вважається повністю завершеною (Done) та готовою до включення в релізний білд лише за умови одночасного виконання наступних бінарних критеріїв:

1. **Критерії приймання виконані:** Усі Acceptance Criteria (AC), зафіксовані в беклозі для даної історії (зокрема позитивні та негативні сценарії), успішно перевірені та підтверджені на тестовому стенді.
2. **Код злито в гілку main:** Реалізація пройшла автоматизовану збірку в CI-конвеєрі, відсутні конфлікти злиття, код влито в основну гілку `main` через Pull Request.
3. **Автоматизовані тести зелені:** Усі модульні (unit) та компонентні тести для нового функціоналу проходять успішно (exit code 0), а загальне покриття кодової бази критичних бізнес-модулів становить не менше 70%.
4. **Самоперевірка за чеклістом наступного дня (Fresh Eyes Review):** Розробник проводить обов'язкову фінальну самоперевірку власного коду за інженерним чеклістом (відсутність хардкоду ключів, валідація null-полів, обробка помилок мережі) вранці наступного робочого дня перед закриттям задачі. Ми свідомо відмовилися від обов'язкового блокуючого peer review другою людиною для кожної мінорної задачі через обмежений ресурс команди.
5. **Контракти API та міграції задокументовані:** Зміни в локальній базі даних SQLite супроводжуються валідною міграцією зі збереженням зворотної сумісності кешу, а зміни у форматах обміну даними відображені в API-специфікації.
6. **Демонстрація працездатності (Demo Ready):** Функціонал історії продемонстровано на фізичному або емульованому пристрої в умовах як стабільного підключення, так і в автономному режимі польоту.

## 2. Чого DoD свідомо не вимагає

З метою збереження високого темпу розробки в умовах обмеженого бюджету та стислих термінів першого релізу (8 тижнів), наш DoD свідомо виключає наступні надлишкові формальні вимоги:

1. **100% покриття коду тестами:** Ми не вимагаємо повного покриття тестами декларативного UI, простих анімацій переходу та згенерованих ORM-сутностей. Вимога до покриття зосереджена виключно на критичних модулях: парсері розкладу, алгоритмі синхронізації та системі автентифікації.
2. **Офіційний зовнішній аудит безпеки перед кожним Pull Request:** Повний аудит зовнішньою службою захисту інформації проводиться комплексно лише перед випуском фінального релізу REL-1, а не для окремих проміжних збірок у ході спринтів.

## 3. Як це працює на практиці

У ході завершених Спринту 1 та Спринту 2 команда застосовувала цей регламент на практиці:

- Із 5 запланованих історій Спринту 1 (S-01, S-02, S-03 та супутні технічні задачі) 4 історії повністю та беззастережно задовольнили всі 6 критеріїв Definition of Done.
- Для історії `S-01` («Вхід акаунтом академії») під час Спринту 1 було свідомо допущено відхилення від ідеального стандарту безпеки: тимчасове збереження токенів у стандартному сховищі налаштувань замість апаратного сховища ключів Keystore заради дотримання термінів демо-дня. Це відхилення було негайно зафіксовано в реєстрі технічного боргу під ідентифікатором `D-01` із зобов'язанням виплатити його у Спринті 3.

---

## 4. Хто ухвалює відхилення від DoD

1. Будь-яке тимчасове відхилення або послаблення критеріїв Definition of Done може бути санкціоноване виключно **Project Manager (PM) проєкту за письмовим погодженням із Замовником (ST-01)**.
2. Жодна історія не може отримати статус `Done` з невиконаними критеріями без обов'язкової реєстрації відповідного запису в реєстрі технічного боргу (`lr11_risks_quality/techdebt.csv`) із зазначенням конкретного власника, оцінки трудомісткості та цільового спринта погашення (`due_sprint`).

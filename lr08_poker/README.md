## 1. Формат і масштаб

### Параметри оцінювання
- **Шкала оцінювання:** Модифікована послідовність Фібоначчі: **`0, 1, 2, 3, 5, 8, 13, 21, ?`**.
- **Склад оцінювачів:** Три погляди на кожну історію — `optimistic` (найкращий сценарій без несподіванок), `likely` (найбільш імовірний хід розробки), `pessimistic` (найгірший сценарій із технічними блокерами та граничними випадками).
- **Метод усереднення:** Формула трьох точок PERT:  
  $$\text{PERT} = \frac{O + 4 \times M + P}{6}$$
  Отримане значення округлюється до найближчої картки шкали Фібоначчі (у разі точного збігу з серединою інтервалу — у більшу сторону на користь запасу надійності).

### Історія-якір масштабу (Anchor Story = 3 points)
Якорем відносного масштабу для команди обрано історію **`S-02` («Вибір своєї групи»)**:
- **Оцінка якоря:** $O = 3$, $M = 3$, $P = 3 \rightarrow \mathbf{3 \text{ Story Points}}$.
- **Чому саме вона:** Це класична інженерна задача з мінімальною невизначеністю: створення трьох стандартних селекторів випадаючого списку (факультет, курс, група) та збереження вибору в локальній базі SQLite на пристрої. Тут немає складного мережевого обміну чи криптографії.
- **Як використовується якір:** Будь-яка інша історія калібрується відносно `S-02`:
  - Якщо задача простіша (наприклад, тумблер тиші в `S-07`) — вона отримує **2 points**;
  - Якщо задача вимагає побудови багатоекранного UI або локальної реляційної моделі (як `S-03` чи `S-04`) — це **5 points**;
  - Якщо задача містить непередбачувані зовнішні інтеграції з брудними даними (як `S-09`) — це **8 points**.

### Чому Story Points — це не людино-години
Story Points вимірюють **відносний розмір, складність і ступінь технічної невизначеності**, а не астрономічний час. Людино-години варіюються залежно від того, хто саме виконує задачу (Senior чи Junior), тоді як відносна складність задачі відносно якоря залишається незмінною. Спроба прирівняти поінти до годин руйнує психологічну безпеку оцінювання та спотворює ризики.

## 3. Конверт 1: переоцінка після нової інформації

### Історія, що зазнала переоцінки: `S-09` («Імпорт розкладу з системи деканату»)

- **Оцінка в Раунді 1 (до відкриття Конверта 1):**
  - Оцінки команди: $O = 3$, $M = 3$, $P = 5$
  - Розрахунок PERT: $\frac{3 + 4 \times 3 + 5}{6} = \frac{20}{6} = 3.33 \rightarrow$ **3 Story Points**.
  - *Початкове припущення:* команда вважала, що API деканату повертає валідований JSON-масив із регулярною сіткою пар.
- **Нова інформація Конверта 1:**
  - Навчальна частина надала реальний дамп бази, де виявлено масові дублікати занять, відсутні (null) прізвища викладачів, неоднозначні назви аудиторій (наприклад, «ауд. 312 / спортзал») та нерегулярні пари з довільним часом.
- **Оцінка в Раунді 2 (після Конверта 1):**
  - Оцінки команди: $O = 5$, $M = 8$, $P = 13$
  - Розрахунок PERT: $\frac{5 + 4 \times 8 + 13}{6} = \frac{50}{6} = 8.33 \rightarrow$ **8 Story Points** (зростання на **+5 points**, тобто на 167%!).
- **Що саме подорожчало в інженерній частині:**
  1. Необхідність написання спеціалізованого модуля санітизації та валідації вхідних даних (Data Cleaning Pipeline).
  2. Алгоритм дедуплікації занять при співпадінні дати та групи.
  3. Обробка `null`-значень викладачів та підстановка дефолтних заглушок («Викладач уточнюється»).
  4. Механізм локального карантину для пошкоджених записів розкладу, щоб збій одного рядка не зупиняв імпорт усього семестру.
- **Вплив на інші модулі:**
  Зміни прямо зачіпають історію `S-03` (Розклад на сьогодні) та `S-08` (Офлайн-кеш), де клієнтський інтерфейс тепер зобов'язаний стійко відображати картки занять із неповними метаданими без виклику винятків NullPointerException.

## 7. Що я зрозумів про свій беклог

1. **Діапазонне оцінювання зриває ілюзію простоти:**  
   Поки задача `S-09` розглядалася як просто «імпорт JSON», вона здавалася легковажною задачею на 3 поінти. Тільки розгляд песимістичного сценарію та реальні дані навчальної частини показали, що нормалізація брудної бази подвоює реальну трудомісткість.
2. **Технічні ризики формулюються мовою бінарних питань:**  
   Найкращий спосіб зняти розкид в оцінках між розробниками — не сперечатися про числа, а сформулювати конкретне технічне питання (наприклад: *«Чи віддає API деканату HTTP-заголовок Last-Modified?»*). Відповідь на таке питання за 15 хвилин тесту знімає невизначеність і звужує оцінку з 13 до 5 поінтів.
3. **Запас ємності — запорука психологічного спокою команди:**  
   Наявність 35% запасу місткості (39 поінтів проти стелі у 60) дозволяє команді спокійно сприймати поглиблення оцінок складних модулів без стресу, нічних авралів та погіршення якості коду.
